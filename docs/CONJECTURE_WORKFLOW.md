# Conjecture investigation workflow

`ResearchAgent.propose` creates an editable nine-stage plan. `ResearchAgent.run` calls `ConjecturePipeline`, which checkpoints each completed stage in SQLite. The API, job queue, Crossref and arXiv clients, PDF ingestion, passage store, model provider, accounting, trace exporter, and Python executor are reused.

All LLM instruction templates, including experiment recovery prompts and the shared paper-context suffixes, are in `researchpilot/prompts.py`. `researchpilot/conjecture_pipeline.py` assembles the stage-specific JSON payloads and response schemas.

`prompts.OUTPUT_FIELDS` explains the exact response fields for every initial and repair call. The pipeline recursively validates returned fields against its response schema before consuming them. Regression coverage is in `tests/test_pipeline_contracts.py`.

Every provider call in an investigation receives bounded, source-identified passages from attached papers. Passage selection favors an algorithm definition relevant to the question, then adds retrieved context. The complete ingested paper remains in the persistent passage store, while model calls receive selected excerpts rather than the entire paper. Evidence excerpts must still be quoted from the specific passage being classified.

After literature search, every later provider call receives a source catalog with IDs, titles, bounded abstracts, attachment status, and full-text inspection status. Whenever inspected or reviewed context exists, calls also receive source-identified passages or abstracts, text scope, relevance summaries, limitations, and grounded findings with locations and assumptions. This includes experiment planning, code generation, result interpretation, synthesis, and qualitative judgment, even after a worker restart. A relevant method paper remains in context even when its review contains no claim-bearing quotation. Unreviewed search hits remain metadata, not evidence.

| Stage | Stored result | Boundary |
| --- | --- | --- |
| Interpretation | `Conjecture`, assumptions, ambiguity | Provider receives bounded, source-identified passages from attached papers and assesses whether they define a testable method; conservative fallback |
| Initial reasoning | Unverified supporting or contradicting observations in `general_reasoning`, each linked to retrieved or supplied `source_ids`; `reasoning_source_ids` | The OpenAI reasoning call can use the hosted web search tool to independently find and inspect corroborating primary sources. Each observation's `source_urls` must match API-returned search sources or citation annotations before it can create a source record. Providers without web search retain the focused Crossref/arXiv query fallback. Mathematical reasoning is not an extracted source finding |
| Additional literature search | Three general scholarly queries in `literature_queries`; `additional_literature_source_ids` | Crossref and arXiv retrieve additional candidates. The source-selection substep automatically includes attached and reasoning sources, then fills remaining review slots from these additional candidates. `selected_source_ids` determines which papers evidence extraction reviews; bounded-mode tool and paper limits apply |
| Evidence extraction | Source relevance reviews and `EvidenceItem` with a source location | One provider call reviews all selected sources; unavailable text is recorded as unknown relevance and a limitation. Each excerpt must occur verbatim in that source's supplied passage or abstract, and abstracts cannot be classified as proofs |
| Experiment planning | `ExperimentDesign` | Provider receives attached method passages and reviewed findings; it creates design metadata, then requests experiment and visualization code together. A valid design is retained if code generation fails. Limited/Restricted limits still apply |
| Execution | `ExperimentResult`, measured evidence, errors, chart | Provider-generated experiment code requires Docker; after `result.json` is validated, a separate Docker run executes visualization code against that file and validates its SVG output; an LLM interprets only recorded measurements |
| Synthesis | `ConjectureAssessment` and synthesis summary | Evidence groups remain traceable; an LLM summarizes conflicts, qualifications, and gaps |
| Qualitative judgment | Free-text `judgment` and `rationale` | The synthesis model assesses the exact conjecture against recorded evidence and its scope; unavailable or invalid responses remain explicitly unavailable. No probability or fixed verdict category is assigned |
| Report | Markdown report | Uses persisted evidence and metrics only |

Source deduplication remaps the reasoning-to-source links and search provenance to the surviving records, including records with matching DOIs but different titles. `source_aliases` retains the mapping from old IDs; trace outputs remain snapshots of the stage that recorded them. Source selection has its own checkpoint and trace entry within the additional literature search stage; it does not add a tenth step to the investigation map. The default Limited/Restricted model-call limit is ten: nine visible stages include a separate source-selection call and an experiment-code call, while the final report is rendered without an LLM call. The pipeline reserves calls for result interpretation, synthesis, and qualitative judgment. If automatic sources exceed the paper review limit, the run records the omitted review as an unresolved limitation. Reports retain the reasoning source references and label the observations as unverified leads.

Web search is enabled only for Initial reasoning. The model may make up to four hosted tool calls in Full mode; Limited and Restricted modes reserves three additional literature searches and one paper download from its tool-call allowance. Search-enabled responses use separate cache entries that preserve retrieved source metadata; cache hits do not count as live searches or incur another search charge. Bounded-mode budget admission reserves hosted search charges, and accounting records actual search usage. The Sources page and report link both paper and web references. arXiv discoveries can proceed through the existing PDF download and passage-review path; web references without retrieved passages remain unverified leads.

## Experiment inspection and reuse

The Experiments page shows each planned design even when execution is skipped. It displays the selection rationale, hypothesis, independent and dependent variables, controls, working assumptions, baselines, exact parameter values and seeds, expected support and contradiction, confounders, limitations, and any recorded run outputs.

The plan stores `ExperimentDesign.code` and `ExperimentDesign.visualization_code` when code generation succeeds. The provider supplies the rationale, variables, baselines, metrics, seeds, assumptions, controls, confounders, algorithm steps, experiment code, and chart code; the UI displays the recorded algorithm steps and both scripts. For a claim classified as experimentable, an unusable plan or invalid code gets a bounded revision attempt, and a failed execution gets one code repair attempt. Users can inspect, copy, or download the experiment code; execution requires the Docker executor. If code generation fails, the design remains visible with an unresolved question explaining why it could not run. Executed `result.json` files can contain general JSON measurements. Recognized paired arrays also receive validated numerical summaries. The visualization script reads the validated `result.json` in a second isolated run and writes `visualization.svg`; the SVG is checked before appearing as an artifact. A chart failure is recorded without discarding the measured result. The provider interprets the executed JSON and names the exact JSON pointers used as evidence; invalid pointers prevent that interpretation from becoming experimental evidence. When interpretation is unavailable, measurements remain recorded without a claimed relation to the conjecture.

The confidence stage asks the synthesis model for a calibrated prediction that the exact conjecture is true, using extracted literature evidence, executed experimental evidence, assumptions, and unresolved questions. The dashboard and report show **very likely false**, **likely false**, **uncertain**, **likely true**, or **very likely true**, immediately followed by a short summary of the literature findings and experimental direction. The model's specific rationale also appears in the report. If no usable model response is available, the label stays uncertain while the description summarizes the recorded evidence. These labels are evidence assessments, not proofs or validated Bayesian probabilities.

The report and Sources page use the same persisted evidence items. They separate direct support, contradictions, qualifications, and related findings that neither support nor refute the claim. Each source card gives an extractive summary from its retrieved abstract when available; it labels sources without classified findings as candidates rather than implying they support the conjecture. Older completed conjecture reports are rendered with the current section layout and qualitative assessment when loaded.

## Evaluation cases

`researchpilot/evaluation_data/conjectures.json` includes established, false, conditional, unresolved, vague, computational, and non-small-computational examples. The offline tests exercise ranking, scoring limits, checkpointing, and provider-generated plans. Live retrieval and model classification quality require a configured provider and network access; review source passages and citations before using assessments for research decisions.


The final provider assessment returns free-text `judgment` and `rationale`, without probabilities or fixed verdict categories. For example: "Supported in the tested setting; broader generality unresolved." Reports and the investigation map display this wording. Earlier numeric snapshots remain readable, but no verdict is derived from their scores; resynthesize a saved investigation to generate a new qualitative judgment. The internal `confidence_estimation` stage identifier is retained for trace and job compatibility.
